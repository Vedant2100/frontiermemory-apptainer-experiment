## Apptainer and Harbor adaptations

- Harbor's Apptainer backend does not enforce Harbor's task network allowlist. The generated memory task copy sets public networking to make Harbor accept the backend, while the memory prompt prohibits network access. This is not equivalent to enforced egress isolation and must be disclosed as a nonstandard exploratory setup.
- The task image uses the local `pycqa-docformatter-141.sif` base because container registry DNS failed. `containers/memory-task-v1.0-localbase.def` copies the pinned v1.0 evidence, links `/usr/bin/python3` to the base image's Python 3.10, and installs FastAPI/Uvicorn from locally downloaded wheels. The resulting `containers/memory-task-v1.0-serverdeps.sif` lets Harbor's server start offline. The benchmark task and verifier are untouched.
- Harbor's Mini-SWE-Agent 2.4.6 setup normally downloads uv, Python 3.12, and the agent from inside the task container; task-container DNS cannot reach Astral/PyPI. Official uv-managed CPython 3.12.15 and Mini-SWE-Agent 2.4.6 are provisioned once under `runtime/uv/`, with a package lock in `configs/mini-swe-agent-requirements.lock`.
- `bin/singularity` binds that persistent tool environment into Harbor containers, redirects uv/XDG/Mini-SWE config paths to the tool directory or container `/tmp`, and sets `UV_OFFLINE=true`. `runtime/uv/bin/uv` appends LiteLLM's declared `mcp>=2.2.0,<3` extra on `uv tool install`; LiteLLM 1.106.3 imports its MCP handler when Mini-SWE sends its bash tool, while Harbor's unmodified bootstrap omits that optional extra. `runtime/uv/bin/mini-swe-agent` clears the task image's Python 3.10 `PYTHONPATH` before starting the Python 3.12 agent, preventing a Pydantic binary mismatch. Harbor and Mini-SWE source code are unchanged.
- The memory-generation prompt has its own Mini-SWE configuration so it does not inherit the generic coding-task completion ritual. Coding condition A/B will continue to use the same coding-agent configuration; only memory consolidation uses the specialized memory prompt.

## Corpus inspection and memory generation (before the target task was fetched)

- The local corpus inspection confirmed 674 files in mixed JSON/JSONL formats. The model should not receive unbounded raw `head`/`grep` output.
- `scripts/summarize_frontiermemory_corpus.py` produces aggregate counts and ten deterministic compact file summaries with command arguments and conversation text omitted. The first parser pass mistakenly treated JSONL `exec` tool inputs (JavaScript tool orchestration) as shell commands; the parser was narrowed to explicit shell-tool names and executable-token syntax before producing the current digest.
- The official corpus card says filenames are random and opaque and provides no map to tasks. The memory prompt discloses that limitation and does not claim the ten samples span different tasks. It warns that combined command counts do not prove efficacy.
- `data/evidence-summary.md` is 6,527 bytes and derives from all 674 v1.0 records; it contains aggregate metadata, ordered executable-token sketches from ten evenly spaced files, and command-family counts for the 100 Mini-SWE-Agent histories. The Mini-SWE subset has 100 PASS markers, so it cannot show which actions caused success. The digest contains no conversation text, paths, code, command arguments, or answers. Its sum of logical file sizes is 314,063,575 bytes; filesystem allocated size is lower (~163 MiB).
- A memory-only bind in `bin/singularity` is enabled with `FM_BIND_EVIDENCE_SUMMARY=1` in the memory-generation Slurm script. Future coding runs leave that variable unset so condition A cannot see the digest.
- Slurm jobs `298733` and `298734` completed the bounded-evidence Harbor runs described above. Both passed only the memory file structure check and failed human semantic review. Job `298735` switched to direct local Ollama API synthesis but still emitted unsupported generic advice; its post-run format check used the wrong path. Job `298768` failed to satisfy a strict JSON section schema. `scripts/generate_memory_from_evidence.py` now requests exactly one rule per eight observed command families, validates the evidence-to-command mapping, saves the raw local model response, and renders fixed Markdown headings. This is a nonstandard direct local-model memory synthesis; Harbor Mini-SWE remains the planned task agent for both coding conditions.
- `frontier-memory check-memory` was rerun with the correct parent directory for job `298735`: its structure passed, but the directory also contained five files because metrics and GPU/model logs sat beside `MEMORY.md`. Future direct-generation runs separate a clean `memory/` directory from `run/` metadata so the task agent receives only `MEMORY.md`.
- Slurm job `298771` is the first memory accepted for the exploratory comparison. It used the local 7B Q4 Ollama model through the direct API with a strict JSON output schema; the script validated the exact command/frequency mapping and rendered one clean Markdown file. Human review found the resulting rules narrow but not fabricated; they define common uses of command families that appeared in the official data and include the counts and subset limitations. This is much weaker semantic memory than a synthesis from full trajectory conversations, so report it as a material experiment limitation.
- The generated memory was manually inspected and passed `frontier-memory check-memory` with one file. The acceptance was based on its eight observed-command practices, not on Harbor's numeric reward alone. The artifact is a weak command-frequency summary; no claim of causal best practice or task-specific knowledge is supported.
- After this review, the official v1.0 task dataset was downloaded, the preferred target and original verifier hashes were recorded, and the paired Harbor runs were completed as described in the later sections and `experiment-status.md`.
